# Design Decisions

The main choices behind the build, and why. Newest last.

## Initial plan

| # | Decision | Why | Instead of |
|---|----------|-----|------------|
| 1 | **The bridge passes lines through as-is** — it never parses or converts a message | Usable by any project without code changes; the message format belongs to the project, not the bridge | Parsing each line and rebuilding it as JSON (ties the bridge to one project's line types) |
| 2 | **Per-project settings live in the project's own repo** — topics, Wi-Fi, broker address and certificates; the bridge repo holds none of them | One branch of bridge code for every project; a project's topics stay with that project; secrets can't be committed anyway | A branch per project in the bridge repo (every fix merged into every branch; the bridge repo knows about every project) |
| 3 | **No git submodule** — a project's docs say "build the bridge at this tag with these config files" | The settings sit outside the bridge's code, so nothing needs nesting inside the project's repo | The bridge as a submodule of each project |
| 4 | **Versions marked by git tags; each project names the tag it was built against** | Later bridge changes can't break a project — it stays on its tag until deliberately moved | Projects building the bridge's latest commit |
| 5 | **Uplink routing by a first-letter table in the project's config** — e.g. `W` → a readings topic; the whole line is published unchanged | The bridge reads one character and nothing else, so it stays format-agnostic while each line type still gets its own topic (per-topic permissions) | The MCU naming the topic on every line (firmware must know topic names, longer lines) · One topic for everything (no per-topic permissions) |
| 6 | **Time line is an optional feature, off by default** — when switched on, the bridge gets the time via NTP and writes it down the UART on connect and at a set interval | The bridge is the part with network access next to the MCU, so the time arrives without network delay and needs no server job; off by default keeps it pure pass-through | A server job publishing the time to a topic (arrives late, extra service) |
| 7 | **Connects to any MQTT broker over TLS with client certificates** — address, port, CA certificate, client certificate and key from the project's config | One code path covers a local Mosquitto and AWS IoT Core, so a project can test locally before the cloud | AWS IoT Core only (can't be tested locally) · An extra unencrypted mode (another mode to build and test) |
| 8 | **Settings compiled in from headers kept in the project's repo** — a config header and a secrets header; the build is pointed at that folder | No file system, parser or provisioning code on the ESP32; certificates never sit in a readable file on the board | A settings file on the ESP32's flash (file system + JSON parser, readable certificates) · Settings typed in over USB serial (most code, awkward for certificates) |
| 9 | **Written on ESP-IDF** | Its MQTT client publishes at QoS 1 and queues unsent messages; Wi-Fi and MQTT reconnect in the background, so the UART keeps being read during an outage; flash encryption and secure boot are properly supported | Arduino with PubSubClient (publishes at QoS 0 only; reconnects block in `delay()` loops) · ESP-AT firmware (not available for the ESP32-S3; the MCU would have to drive Wi-Fi, MQTT and certificates itself) |
| 10 | **Built with PlatformIO using the ESP-IDF framework** | Same editor, build and flash workflow as the MCU projects that use the bridge | Espressif's own `idf.py` tooling (separate install and a second workflow) |
| 11 | **No backlog in the bridge** — a line that arrives while Wi-Fi or the broker is down is dropped | The bridge is an extension of the board using it, not a separate device: bridge down is the same as the board being offline. The board keeps gathering data and owns any storing and resending | A queue in the bridge's RAM (lost on reset; a second place where reliability is handled) |
| 12 | **Testable on its own with dummy data** — no MCU project has to exist | The bridge can be proven and tagged before anything depends on it, and a fault can be pinned on the bridge or on the project | Testing only once wired to a real project's firmware |
| 13 | **Standalone test broker: Mosquitto with TLS + client certificates in a Multipass Ubuntu VM** | The VM has its own address on the network, so the ESP32 reaches it directly over Wi-Fi; no cloud account or cost | Mosquitto in WSL (port forwarding + firewall rule through Windows) · Mosquitto installed on Windows |
| 14 | **The bridge repo is local-only** — no AWS resources; a first AWS IoT Core connection is made by the project that uses the bridge | IoT Core is one more TLS broker with client certificates, already covered by the local test; no cloud account, infra code or cost here | A cloud phase in the bridge repo (AWS setup and cost to re-prove the same code path) |
| 15 | **Named `uart-mqtt-bridge`; scope is UART ↔ MQTT only** | The name states the two interfaces it has; Wi-Fi is only the transport to the broker | `wifi-bridge` (suggests general Wi-Fi access such as HTTP, which it doesn't provide) |
| 16 | **Link-status line to the MCU, optional and off by default** — a line down the UART when the link goes up or down | The MCU can show the link state or stop sending without the bridge needing to understand the project | The MCU inferring the link state from missing replies |
| 17 | **Status LED** — on-board RGB shows link state and blinks on traffic | The bridge's state is visible on the bench with no serial monitor open | Serial log only |
| 18 | **Firmware build in CI** — GitHub Actions compiles every push | A tagged version is known to build from a clean checkout | Building only on the development PC |
| 19 | **Flash encryption + secure boot in the core build** | The Wi-Fi password and the client private key are compiled into the firmware; without encryption they can be read straight off the flash chip | Leaving the flash readable |

## During the build

| # | Decision | Why | Instead of |
|---|----------|-----|------------|
| 20 | **The test VM sits on Hyper-V's Default Switch; Windows forwards port 8883 to it** — the ESP32 connects to the PC's Wi-Fi address | Multipass doesn't offer the PC's Wi-Fi adapter for bridging, and the PC is on Wi-Fi; forwarding one port still keeps the broker in a VM | A bridged VM with its own address on the network (needs a wired Ethernet connection) · Mosquitto installed on Windows |
| 21 | **Status LED driven with ESP-IDF's built-in RMT driver** — no added component | The firmware stays free of outside dependencies; one small function sets the colour | Espressif's `led_strip` component (an extra dependency to fetch and pin for a single LED) |
| 22 | **Status LED uses four colours: red, amber, green, blue** | A small fixed set is told apart at a glance | A wider palette of colours |
| 23 | **The full `sdkconfig.genesis-mini` is committed** | A clean checkout and CI build the firmware with exactly the settings it was tested with, including the 4 MB flash size | A hand-written `sdkconfig.defaults` with the generated file ignored (a second file to keep in step with menuconfig) · Leaving it out and listing the settings in the docs |
| 24 | **A line longer than the limit is dropped whole and logged** — nothing of it is passed on | The bridge passes lines through unchanged; a cut-off line would reach the broker looking like a valid message | Passing on the first part of the line (publishes a corrupted message) |
| 25 | **The test broker's certificates are created by a script kept in this repo** — the Linux tools it uses (`openssl`, `ssh`) run in WSL | The same steps are repeated for every test broker and whenever a broker's address changes; a script gives the same result each time, and it ships with the firmware that needs the certificates | Typing the `openssl` commands by hand on each VM |
| 26 | **The script reaches the broker's VM over SSH** — `scp` to copy files, `ssh` to run commands | Works with any Linux host, not only a Multipass VM, and is the same link other tooling such as Ansible uses | `multipass transfer` / `multipass exec` (ties the script to Multipass) |
| 27 | **The CA is kept on the PC (in WSL), outside the repo and outside the VM** — the broker gets only the CA certificate, its own server certificate and key | A VM can be deleted without losing the CA, and the CA certificate and client certificate built into the firmware stay the same from one test broker to the next | A new CA created inside each VM (lost with the VM; the firmware's certificates change per broker) |
| 28 | **Secrets are split by what they hold, in `include/secrets/`** — `wifi.h` (network name and password, filled in by hand) and `certs.h` (CA certificate, client certificate and key, written by the certificate script); both gitignored, each with a committed example file | The script can rewrite the certificates on every run without touching the Wi-Fi details, and each file's name says what is in it | One `secrets.h` holding everything (the script would have to edit a file that is also edited by hand) |
| 29 | **The broker address and port sit in the config header, not with the secrets** — the config header is gitignored, with a committed example file | They are settings, not secrets or certificate data; keeping one project's values out of the repo leaves only a neutral example for anyone using it | Putting them in `certs.h` (mixes settings into a generated secrets file) · Committing the config header (one project's values in the repo) |
| 30 | **The certificate script is re-runnable and finds the PC's current address itself** — each run replaces the old values wherever they are used, and it can remake every certificate from scratch | A changed address is fixed by one command with nothing typed in; a suspected leak is handled by throwing all the certificates away and making new ones | A fixed address reserved on the router (depends on a setting outside the repo; breaks on any other network) · Passing the address in by hand |
| 31 | **The setup is started by a Bash script on the PC (Git Bash), which runs the WSL part** — it switches on forwarding between WSL's virtual network and the VM's only while it works on the VM over SSH, then switches it off again | WSL and the VM sit on separate virtual networks that Windows doesn't pass traffic between by default; the script makes that change itself, so a new VM needs no manual network setup, and the PC is left as it was found | Starting the script inside WSL (the forwarding has to be set up by hand first) · Leaving forwarding switched on permanently |
| 32 | **Each developer keeps their own config file** — `scripts/config.sh` is gitignored and copied from the committed `config.example.sh`; it holds the PC's network adapter names among the other settings | Adapter names and the choice of system differ from PC to PC; the repo holds only a neutral example, and the scripts run with nothing passed in | Adapter names fixed in the scripts · A committed config holding one PC's values · Passing the names in on every run |
| 33 | **The setup scripts read their settings from one config file** — the VM's name, the adapter names, and whether the PC is Windows; the Windows flag decides whether the forwarding step runs | The script is started with no arguments; everything Windows-specific sits behind one flag, so the same scripts run on Linux with that step skipped | A list of arguments on every run · Separate Windows and Linux versions of the scripts |
| 34 | **A working WSL is a stated prerequisite on Windows; the scripts don't check for it** | The scripts stay focused on the certificate setup; installing and fixing WSL is outside what they can do anyway | A WSL check at the start of the script |
| 35 | **The PC's LAN address is found with each system's own network tool** — `netsh` on Windows, `ip` on Linux, chosen by the Windows flag | The setup scripts need nothing installed beyond Bash and the tools the system already has | A single Python command that works on both (adds Python as a requirement for one lookup) |
| 36 | **The SSH key and the certificates are kept in folders named for the project** — `~/.ssh/<project>/` and `~/certs/<project>/` | Nothing is mixed in with the developer's own keys, and removing a project's setup means removing exactly those two folders | A general-purpose key in `~/.ssh` · One shared certificate folder |
| 37 | **Settings are read from the config once and passed into each function as arguments** | A function's argument list shows everything it depends on, and the functions hold no project-specific values | Functions reading the config's variables directly |
| 38 | **The port rule listens on the PC's LAN address only** | Only connections arriving on the local network's address are passed on to the VM | Listening on every address the PC has |
| 39 | **The broker's VM is created by a script, and another script deletes everything the setup created** — the setup script runs them itself with `--create-vm` and `--nuke` | The whole setup is proven from nothing with one command, and a setup in doubt is replaced, not repaired | Creating the VM and cleaning up by hand |
| 40 | **The port rule and the firewall rule are removed again after the test, unless `--keep-alive` is given** | The PC is left closed by default; the port is open only when a device test asks for it | Leaving both rules in place after every run |
| 41 | **The setup ends with a TLS connection test through the PC's LAN address, using the client certificate** | It takes the same path a device takes, so the address, port rule, firewall rule and certificates are all proven before any firmware is involved | Finding a setup fault later, from the device |
| 42 | **The scripts are one setup script, helper files of functions grouped by subject, and standalone scripts — all run from `scripts/`** | The setup script reads as the list of steps, and one run location keeps every path the same | One long script · A different run location per script |
| 43 | **A git pre-commit hook kept in the repo refuses commits that would add secrets** — any file in `include/secrets/` except the examples, `scripts/config.sh`, or a private key in any file; switched on once per clone with `git config core.hooksPath .githooks` | A second guard behind `.gitignore` in case an ignore line is removed or a secret is pasted into the wrong file; it is plain Bash, so nothing has to be installed | The pre-commit framework or gitleaks (extra software on every PC) · GitHub secret scanning (only catches the secret after it has been committed and pushed, and doesn't recognise a Wi-Fi password) · `.gitignore` alone |
| 44 | **The LED shows the Wi-Fi link: red = not connected, amber flashing = connecting, green = connected** | The link state is read at a glance, and the flashing tells "trying" apart from "given up for now" | Logging the link state only (needs a serial monitor open) |
| 45 | **After a drop, the bridge waits 5 s before connecting again** | Retries don't run back to back while the network is down, and the red LED stays on long enough to be seen | Connecting again straight away |
| 46 | **The firmware's certificates are kept as the PEM files themselves — `ca.crt`, `client.crt`, `client.key` in `include/secrets/` — copied there unchanged by the setup script** (reverses #28's `certs.h`) | Nothing is converted, so every setup run leaves the firmware's copies matching the broker's, and the files stay usable as they are with other tools | The script writing a `certs.h` of C strings (a Bash script generating C) · Copying them in by hand after every run |
| 47 | **The broker's address and port are written by the setup script into `include/secrets/broker.h`** (replaces #29's hand-edited config header) | The script already finds the PC's current LAN address on every run, so the firmware always points at the right address with nothing typed in; the folder is already gitignored and guarded by the hook | A hand-edited config header with an example file (the address goes stale whenever it changes) · The firmware reading `scripts/config.sh` (a Bash file, not usable from C) |
| 48 | **Every file in `include/secrets/` is written by the setup script; the Wi-Fi name and password move into `scripts/config.sh`** (reverses #28's hand-filled `wifi.h` and its example file) | `config.sh` is the one file a developer fills in; the firmware's files are generated from it, so nothing in `include/secrets/` is ever edited by hand and the whole folder is simply ignored. The README states what each file must hold, for anyone not using the script | A hand-filled `wifi.h` with a committed example (a second file to fill in, beside `config.sh`) |
| 49 | **The MQTT client is Espressif's `espressif/mqtt` package from the component registry, pinned to an exact version; `dependencies.lock` is committed** | ESP-IDF 6 no longer includes its MQTT client — this is the same client, now shipped separately. Pinning, plus the lock file's checksum, means nothing changes unless the version is moved deliberately. TLS stays in ESP-IDF's own `esp-tls` and `mbedtls` | Writing an MQTT client on top of `esp-tls` · Going back to an older ESP-IDF that still includes it · An unpinned version |
| 50 | **Green on the LED means Wi-Fi is up: blinking once a second until the broker is connected, solid once it is** (extends #44) | "On the network but can't reach the broker" is told apart from "fully connected" at a glance, using the colour that already means Wi-Fi is up | A separate colour for the broker connection (a fifth state to remember) · Solid green for Wi-Fi alone (a broker fault would look like everything working) |
| 51 | **The board's wiring lives in one header, `include/board.h`** — LED pin, UART port, pins and baud rate — instead of in each module or the project's config header | Moving to another board means changing one file; the module headers stay the modules' interfaces | Defines at the top of each `.c` file (spread across modules) · UART settings in the project's config header (they belong to the board, not the project) |
| 52 | **The modules live in one ESP-IDF component, `components/modules/`, a folder per module holding its `.c` and `.h`; `src/` holds only `main.c`** (plus the certificate embedding, which PlatformIO only accepts there) | Each module's files sit together, the MQTT package is declared next to the code that uses it, and the component lists what the modules depend on — with a single build file for a project this size | Everything in `src/` and `include/` · A separate component per module (a build file each) |
| 53 | **One rule for both directions: a message is one line of at most 127 characters with no `\n`; anything longer, or a downlink message containing `\n`, is dropped and logged** (extends #24 to the downlink) | The MCU always receives exactly one whole line per message, and the limit is the same whichever way the data travels. 127 characters is three times the longest line in use; a project needing more splits its messages in its own format, which the bridge passes through unchanged | No limit on the downlink (a long or multi-line message would reach the MCU as several lines or overflow its buffer) · A larger limit (more RAM for every line buffer) |
| 54 | **On Windows, the setup script starts WSL itself before checking the adapters** (#34 still holds: it doesn't check that WSL is installed or working) | WSL's network adapter only exists while WSL is running, so after a restart the adapter check would fail on a correct setup | Opening WSL by hand before every run |
| 55 | **The config header holds only values, written as lists** — `UPLINK_ROUTES` is a list of `{ letter, topic }` pairs and `DOWNLINK_TOPICS` a list of topic names; the firmware builds its arrays from them | A project's config file contains no types and no code, so it can't break the build in more than one place and reads as a table; it follows `board.h`, which is also values only | Arrays defined in the header (a definition in a header is repeated in every file that includes it) · One numbered `#define` per route (the firmware has to know how many there can be) |
| 56 | **Routing lives in its own module, `router`, between the UART link and the MQTT link** — the UART link hands it each finished line; it looks up the topic and calls the MQTT link's publish | The UART link and the MQTT link know nothing about the table or each other's details, and the lookup is a plain function that can be tested on a PC without the board | The lookup inside the UART link (it would have to know about topics) · Inside the MQTT link (it would have to know about line formats) |
| 57 | **The MQTT link only keeps the connection; everything about messages is in the router** — publishing, subscribing to the downlink topics and handling received messages. The MQTT link hands out its client, and the router listens to the client's events itself (extends #56) | Each module has one job: a change to TLS or reconnecting touches only the MQTT link, and a change to topics or the message rule touches only the router | Publish and subscribe functions in the MQTT link (connection and message handling in one module) · A third module for the message jobs (the table and the code that uses it in separate places) |
| 58 | **The line limit is one value, `LINE_MAX_LEN` in the UART link's header, used for both directions** | Rule #53 is the same limit both ways, so it is written once and can't drift apart | A separate limit defined in each module |
| 59 | **The dummy data source is a module in the firmware that writes numbered lines to the bridge's own UART**, looped back with a jumper from TX to RX; it is switched on by an interval in the config header and is off when that is 0 or absent | The lines pass through the real UART, line reader and router, so the whole uplink is exercised with no MCU attached; a project's config never switches it on by accident | Handing test lines straight to the router (skips the UART and the line reader) · A second board or a PC serial adapter sending lines (more hardware for the same test) |
| 60 | **The bridge is tested end to end by a script, through the broker only** — a dummy line has to arrive on the uplink topic, and a message published to the downlink topic has to come back up | A message on a topic is a clear pass or fail, and it proves the whole chain at once: certificates, port rule, firmware, Wi-Fi, TLS, both directions | Reading the board's serial log (the port drops on reset, and log text is awkward to check) · Running the bench checks by hand after every setup |
| 61 | **One script per job, and `e2e.sh` to run them all** — `nuke.sh`, `create-vm.sh`, `setup-certs.sh`, `build-and-upload.sh`, `test-bridge.sh`, in `scripts/steps/`; `scripts/e2e.sh` runs them in that order, from nothing to a tested bridge (replaces #39's `--nuke` and `--create-vm` options and #42's `standalone/` folder) | Any one step can be run again by itself, each script's name says what it does, and `e2e.sh` reads as the list of steps. `setup-certs.sh` is back to certificates and the connection only | One setup script with an option for every extra step (the script and its options keep growing) |
| 62 | **The scripts are written for Linux and hold no Windows checks; Windows gets its own start script** that does the Windows-only parts (starting WSL, forwarding, the port rule and the firewall rule) and runs the same scripts in WSL (replaces #33's Windows flag) | Each script reads as one straight list of steps and is run on the system it was written for; everything Windows-specific sits in one place | A Windows flag checked throughout the scripts (two paths inside every function, and the Linux path was never run) |
| 63 | **The Multipass and PlatformIO commands are plain values in the config file** — the example shows the Linux and the Windows value, with the one not in use commented out | The config file is already each developer's own, so the choice of system is made once, there, and the scripts just run the command they are given | Working the command names out from a Windows flag |
| 64 | **The functions for the PC's LAN address and the port rule come in a Linux file and a Windows file with the same names; the config file says which one the scripts load** — `iptables` on Linux, `netsh` on Windows, where the port rule also adds and removes its firewall rule (extends #63; replaces #35's Windows flag and #40's separate firewall-rule step) | These are the only steps that differ between the two systems once the scripts run in WSL, so the scripts call one set of names and never ask which system they are on | A Windows check inside each function · The Windows start script setting the rule itself (the setup would need a way to be told to skip its own) |
| 65 | **On Windows, forwarding between WSL's network and the VM's stays on for the whole run of `windows.sh`** and is switched off when it ends (changes #31, which switched it on only around the SSH step) | The start script wraps a whole script and doesn't know where its SSH step begins and ends; the PC is still left as it was found | The Linux scripts telling the Windows script when to switch it on and off |
| 66 | **The pre-commit hook also runs ShellCheck on the staged shell scripts and refuses the commit if one doesn't pass**; without ShellCheck on the PC it says the scripts were not checked and lets the commit through (extends #43) | The scripts change the PC's network settings and delete things, and mistakes such as an unquoted or misspelt name only show when that line runs; the check costs nothing at commit time. The secrets check has to keep working on a PC without ShellCheck | Running ShellCheck by hand (forgotten) · A CI job (reports only after the push) · Refusing every commit when ShellCheck is missing (blocks commits that touch no script's logic on a PC that doesn't have it) |
| 67 | **Work towards `v1.0.0` is collected on a `release/v1.0.0` branch** — pull requests branch from it and merge into it; once the bridge has been run with a microcontroller it is merged into `master`, and that merge is tagged `v1.0.0` | `master` always matches the last release, so anyone cloning it gets a state that was tested as a whole; the changes that come out of driving the bridge with a real device can land as small, reviewed pull requests without each one having to be release-ready. The branch is not named `v1.0.0` because the tag will be, and a branch and a tag with the same name make git commands ambiguous | Pull requests straight into `master` (between releases `master` would hold a partly proven state) · A branch named `v1.0.0` (same name as the tag) |
| 68 | **Logging of the lines themselves is a config setting, `LOG_LINES`** — when it is on, every line received from the MCU is logged as `uart: up: ...` and every line written to it as `uart: down: ...`, both in the UART module; off, neither is logged. Left out of a config, it is off (replaces the always-on `router: down: ...` message) | A project sees what crosses the UART, in both directions, by changing a value in its config, not the firmware's code. Logging where the bytes enter and leave shows a line even when it cannot be routed or the broker is down, and one switch covers both directions. A deployed bridge can run with it off, so a busy link does not fill the log | Raising the log level to debug (also switches on every other module's debug output, and needs the firmware's maximum log level raised) · A message where the line is published (shows nothing for a line that is never published) · Always-on logging (no way to quieten a busy link) |
| 73 | **A project hands the bridge's scripts one folder, kept in the project's own repository, that holds both config files: `config.sh` for the scripts and `config.h` for the firmware** (makes #2 and #8 concrete; changes #32) — with no folder given, the scripts use the bridge's own `scripts/config.sh` and `include/config.h`, which is the bridge standing alone | A project uses the bridge as it is and writes nothing into the bridge's repository, so the bridge's folder never holds a project's values or an edit that has to be kept out of a commit, and it can be updated or cloned afresh at any time. One location covers both files, so there is one thing to pass | The project writing its config into the bridge's folder before each build (the bridge's repository is left with changed files) · Separate config files for standalone and project use inside the bridge's repository (the bridge holding files for projects it does not know) · A separate location for each file (two things to pass and keep in step) |
| 74 | **`config.sh` holds only the values someone has to choose; values that are the same for every setup move into the scripts** — for example the SSH options, which are built from the project name (changes #32, where the config file held everything) | A project's config is shorter and cannot get a fixed value wrong; the fixed values are committed and reviewed with the scripts that use them | Every value in the config file (each project copies values it must never change) |
| 75 | **The certificates stay the bridge's job** (changes #2, which put the certificates in the project's repository) — the bridge's scripts make the CA, client and server certificates for whichever project name the config gives, and keep them in that project's folders on the PC (#36); a project's repository holds no certificate and no script for making one | Making and installing the certificates is the same for every project and is already written and tested here; a project cannot commit a key by accident, because it never holds one | Each project making and keeping its own certificates (the same scripts copied into every project) |
| 76 | **The decisions are kept in two files: `decision_logs.md` is the log, added to and never edited; `finalised-decisions.md` holds the decisions in force, and is rewritten as they change** | The log shows how the design got here, including what was reversed, so it is long and a reader has to follow each "replaces" to see what holds today. The second file states the current design directly, by subject | The log alone (the current design has to be worked out from it) · Editing the log in place (the reasons for earlier choices are lost) |
| 77 | **Windows is supported for the bridge standing alone only** — a project that uses the bridge builds it from Linux, and nothing in the build-from-a-project path handles Windows | The Windows path needs an administrator terminal, WSL, forwarding between two virtual networks and the PC's adapter names. Keeping it to the standalone bridge leaves one path for a project to build and test | Supporting a project's build from Windows too (a second path through every project's scripts, which would not be run) |
| 78 | **Everything for Windows is in one folder, `scripts/windows/`: the start script, its helper functions, the Windows network functions and a config file of its own. `scripts/config.sh` holds only values that are the same on both systems, and the Linux commands are fixed in `helpers/settings.sh`** (replaces #63's commented-out alternatives and #64's config value that chose the helper file; changes #32). The Windows start script names its settings file when it runs a script, and its values take the place of the Linux ones | A Linux user fills in one short config with no Windows line in it, and never opens the Windows folder; nothing is chosen by commenting lines in and out. Removing the folder would leave a complete Linux setup, which shows the two are really apart | Both systems' values in one config file, one of each pair commented out (#63; every user reads and edits settings for a system they do not use) |
